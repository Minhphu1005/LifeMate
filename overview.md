# LifeMate — Voice-Driven AI Agent Challenge

## 1. Overview & Description

Voice is becoming the main way people talk to machines. The next generation of devices — smart speakers, in-car assistants, smart TVs, earbuds, watches, home robots — will have small screens or none at all, yet they will connect to the same apps and services people already rely on. 

* A parent tells the living-room speaker to cool the house before leaving the office;
* A driver asks the car to pay the electricity bill;
* An office worker tells their earbuds to book a ride home after a late meeting;
* A shop owner asks the kitchen speaker to order lunch for the staff;
* A grandparent who never learned to use apps asks the TV to set a reminder to take medicine.

On a phone, each of these tasks takes many taps across several apps; on a screenless device, it is only possible if the assistant can act on its own — yet today’s voice assistants mostly answer questions rather than act. What people want is to simply say it in plain Vietnamese — *“Tôi sắp về nhà, bật điều hòa phòng khách và đặt xe đón tôi”*, *“Chuyển cho mẹ 500 nghìn”*, *“Tắt hết đèn tầng một”*, *“Nhắc tôi họp lúc ba giờ chiều mai”* — and have it done.

**LifeMate** challenges you to build an AI agent that turns spoken Vietnamese requests into actions: given an audio request, the user’s context, and the apps and services connected to the device, the agent plans the steps, calls the right tools with the right arguments, and leaves every app in the state the user asked for — or asks for the missing information when the request is incomplete, and takes no action when no installed app can handle it. 

The agent is judged on what it does, not what it says. The competition data is anchored in everyday Vietnamese digital life (smart home, banking, ride-hailing, food delivery, email) with requests spoken in synthetic and real voices from the North, Central, and South regions. The capability you build is general: voice-driven, multi-step tool use by an AI agent that can run on any device, from phones to smart speakers to cars.

## 2. Input & Output Specification

### Input
- **Spoken request:** An audio file with the user’s latest request in Vietnamese, possibly mixed with common English words (e.g., "book", "AC").
- **User context:** Current time, timezone, location, and a user profile (e.g., home and work addresses).
- **Available apps:** The apps connected to the device (smart home, banking, ride-hailing, food delivery, email, …), each exposing a set of tools described by a JSON schema.
- **Conversation history:** Earlier turns of the same conversation, if any.
- **Simulated environment:** Holding the user’s app data (devices, accounts, reminders, contacts, …), which the agent can read and change only through tool calls.

### Output
The agent produces an ordered list of tool calls (`name` and `arguments`) to handle the user's request. Depending on the request and available information, the agent may:

1. **Execute actions:** Call the necessary tools in sequence to complete the task and achieve the expected final app state.
2. **Request missing information:** Call `sys.ask_missing_info` to specify the intended tool and missing parameters when additional information is needed. This may happen after other tool calls have already been executed.
3. **Handle out-of-scope requests:** Return an empty list of tool calls (`[]`) if none of the available apps can handle the request.
4. **Final state hash:** Along with the tool calls, the agent submits a `state_hash` generated by the execution environment (`env.get_state_hash()`), which is used to verify the final app state.

### Example
- **Input:** 
  - Audio: *“Tôi sắp về nhà, bật điều hòa phòng khách 26 độ và đặt xe đón tôi.”*
  - Context: User is at work (`227 Nguyễn Văn Cừ, Quận 5, TP.HCM`), `user_profile.home` is `123 Trần Hưng Đạo, Quận 5, TP.HCM`.
  - Installed apps: `smart_home`, `ride`, `banking`, `email`.
- **Output:** 
  The agent first reads the device list to find the living-room AC, then sets it and books the ride. The submission line for this sample (one JSON object per line in `submission.jsonl`):

```json
{
  "id": "s_000123",
  "tool_calls": [
    {
      "name": "smart_home.get_status",
      "arguments": {}
    },
    {
      "name": "smart_home.climate_set",
      "arguments": {
        "device_id": "ac_living_room",
        "mode": "cool",
        "temperature": 26
      }
    },
    {
      "name": "ride.book",
      "arguments": {
        "from": "227 Nguyễn Văn Cừ, Quận 5, TP.HCM",
        "to": "123 Trần Hưng Đạo, Quận 5, TP.HCM"
      }

}
```

## 3. Evaluation & Metrics

Each sample is scored on two criteria:
1. Whether the agent leaves the app data in the **correct final state**.
2. How closely its tool calls match the **reference (gold) calls**.

### Metrics Details
- **State match:** The submitted `state_hash` must equal the gold `state_hash`, otherwise the sample scores `0`. Free-text (fuzzy) fields do not affect the hash. The `state_hash` must be computed by the `zaic_tools` environment (`env.get_state_hash()`) and can be reproduced by the organisers, who replay the submitted `tool_calls` in order with the matching version of `zaic_tools`; if the results differ, the organisers' result is final.
- **Tool-call match:** A submitted call matches a gold call when:
  - The tool name is identical.
  - Every non-fuzzy argument is identical.
  - Every fuzzy argument has token-F1 > 0.6 (after lowercasing and Unicode NFC).
  - Each call can match at most one gold call; execution order is not considered in matching.
- **Out-of-scope samples:** If the gold list is empty (`[]`), the sample scores `1` only when the submitted list is also empty; otherwise it scores `0`.
- **Missing information:** `sys.ask_missing_info` is scored like any other tool.

### Scoring Formula

$$
\text{Score} = 
\begin{cases} 
0, & \text{if } \text{hash}_{\text{sys}} \neq \text{hash}_{\text{gold}} \text{ or } M = 0 \\ 
\frac{2 \cdot P \cdot R}{P + R}, & \text{otherwise} 
\end{cases}
$$

Where:
$$
P = \frac{M}{M + U}, \quad R = \frac{M}{|G|}
$$

$$
\text{Final score} = \frac{100}{N} \sum_{i=1}^{N} \text{Score}_i
$$

- $P$: Precision.
- $R$: Recall.
- $M$: Number of matched tool calls.
- $|G|$: Number of gold tool calls.
- $U$: Number of unmatched submitted calls (including calls rejected with a schema error).
- $N$: Total number of samples in the test set.

> [!NOTE]
> If the gold list is empty ($|G| = 0$), the sample scores `1` only when the submitted list is also empty ($M=0, U=0$); otherwise it scores `0`.

## 4. Dataset Specification

The data has three splits with identical layout:
- **`train`:** ~1,600 samples with full labels.
- **`public_test`:** ~600 samples for the public leaderboard.
- **`private_test`:** ~600 samples released after Docker solutions are frozen.

### Folder Structure
```text
<split>/                                  # train | public_test | private_test
├── audio/<id>/<id>.wav                   # spoken request of each sample
├── <split>.jsonl                         # one sample per line
├── <split>_tools_catalog.json            # schema of every app tool
├── <split>_environment/<id>/state.json   # initial app data of each sample
├── sample_submission.jsonl               # public_test only
└── zaic_tools/                           # execution environment library for this split
```

### Files Breakdown
1. **Audio (`audio/<id>/<id>.wav`):** The user’s latest request and every earlier user turn in history, in Vietnamese with common English loanwords (e.g., "book", "AC"). WAV format, 16 kHz, mono, 16-bit; ~100% recorded by real speakers of various ages, genders, and regions (North, Central, South).
2. **`<split>.jsonl`:** Input metadata for each sample:
   - `id`: Unique sample ID.
   - `audio`: Path to the audio file.
   - `context`: `current_time`, `timezone`, location, `user_profile`, `installed_apps`.
   - `history`: Earlier conversation turns.
   - *(Train split only)* `audio_text` (transcript of every user turn) and `label`: gold `tool_calls`, `tool_results`, and `final_state`.
3. **`<split>_tools_catalog.json`:** The apps available in the split and schemas for every tool:
   - Metadata: `name` (`<app>.<tool>`), `description`, `kind` (`read`, `write`, or `meta` for `sys.ask_missing_info`), JSON Schema parameters, and return summary.
   - Annotations:
     - `x-ref`: Must be a valid ID existing in the app data.
     - `x-match: "fuzzy"`: Free text, evaluated by token-F1.
     - `x-one-of`: At least one of the listed parameter groups is required (e.g., `contact_id` or `phone_number`).
   - The catalog covers the whole split; a specific sample may only call tools belonging to its `context.installed_apps`.
4. **`state.json`:** Initial app data (devices, accounts, contacts, reminders, etc.) with history actions already applied, plus a `_meta` block (`question_id`, `current_time`, `tools`). Loaded by the environment.

## 5. Execution Environment (`zaic_tools`)

The organisers provide the `zaic_tools` Python library, which simulates the apps locally. 

- Each sample runs in its own `ToolEnv`, which must be created only once.
- The environment validates each call against the tool schema, executes it, updates internal app data, and returns the result for the agent's next step.
- Failed calls return `{"ok": false, "error": "..."}` (e.g., tool not found, invalid parameter types).
- Only tools from `context.installed_apps` (plus `sys.ask_missing_info`) may be called.
- Every call (successful or failed) is recorded in the tool call log.

### Basic Usage

```python
import sys
from pathlib import Path

# Add zaic_tools of the split to path
sys.path.insert(0, "public_test")
from zaic_tools import ToolEnv

# Create one environment per sample; root is the folder holding split folders
env = ToolEnv("public_test", "public_0001", root=".")

# 1. Validate arguments against schema without executing
validation = env.validate("smart_home.light_set", {"power": "off"})
# -> {"ok": false, "error": "thiếu tham số bắt buộc: device_id"}

# 2. Execute a call
res = env.call("smart_home.get_status", {})
# -> {"ok": true, ...} or {"ok": false, "error": "..."}

# 3. Retrieve call log and state hash for submission
tool_calls = env.get_tool_calls()
state_hash = env.get_state_hash()
```

> [!CAUTION]
> **Strict Environment Rules:**
> - Solutions **must not** read, copy, or parse any file under `<split>_environment/` (including `state.json`).
> - All app data must be accessed solely via `zaic_tools` using exactly one `ToolEnv` per sample.
> - At inference, only `validate`, `call`, `get_tool_calls`, and `get_state_hash` are permitted. 
> - Calling `get_state`, accessing `states`, importing `Executor`/`Simulator`, or cloning the environment is strictly forbidden (`get_state` is allowed during training only).

## 6. Inference & Submission Pipeline

### Inference Template
Run from the root directory containing the split folders:

```python
import json
import sys
from pathlib import Path

ROOT = Path(".")
SPLIT = "public_test"

sys.path.insert(0, str(ROOT / SPLIT))
from zaic_tools import ToolEnv

def infer(item):
    # Initialize exactly one environment per sample
    env = ToolEnv(SPLIT, item["id"], root=ROOT)

    # Pipeline logic:
    # 1. ASR (ROOT / SPLIT / item["audio"])
    # 2. LLM reasoning / tool selection
    # 3. env.call(tool, arguments)
    # 4. Multi-turn agent loop ...
    
    return env.get_tool_calls(), env.get_state_hash()

def main():
    input_file = ROOT / SPLIT / f"{SPLIT}.jsonl"
    output_file = "submission.jsonl"
    
    with open(input_file, encoding="utf-8") as fin, \
         open(output_file, "w", encoding="utf-8") as fout:
        for line in fin:
            item = json.loads(line)
            tool_calls, state_hash = infer(item)
            record = {
                "id": item["id"],
                "tool_calls": tool_calls,
                "state_hash": state_hash
            }
            fout.write(json.dumps(record, ensure_ascii=False) + "\n")

if __name__ == "__main__":
    main()
```

### Submission File Format
The submission file must be UTF-8 JSON Lines with exactly one line per sample.

```jsonl

{"id": "public_0001", "tool_calls": [{"name": "sys.ask_missing_info", "arguments": {"tool_name": "music.add_to_playlist", "params": ["playlist_id", "track_id"]}}], "state_hash": "c83200c2…"}
{"id": "public_0002", "tool_calls": [], "state_hash": "0c9a2ec0…"}
```

## 7. Competition Rules & Guidelines

### Competition Rounds
- **Round 1 — Public Test:** Teams develop solutions, evaluate on `public_test`, and submit `submission.jsonl` to the public leaderboard (reference only).
- **Final Solution Submission:** The solution is submitted as a Docker image according to separate guidelines. Organisers mount the private test folder into `/data`, run inference, and collect output at `result/submission.jsonl`. Container must run **fully offline with no network access**.
- **Round 2 — Private Test:** Organisers release `private_test` and its environment. Teams run their frozen solution and submit results. Organisers re-run the Docker image to verify results. Final rankings are based strictly on private test evaluation.

### Technical Constraints
- **Model Size:** 
  - Entire system (ASR + LLM + all other components): $< 6\text{B}$ parameters in total.
  - LLM alone: $< 5\text{B}$ parameters.
  - Maximum context length: $\le 16\text{K}$ (16,384) tokens.
- **Data Access:** No direct reading of `state.json`. All interactions must happen through `ToolEnv`.
- **Allowed Data & Pretrained Weights:**
  - Public data and open-source models released **before 26 October 2026** with compliant licenses.
  - Synthetic data generated via external LLMs/TTS is allowed **during development only**, never at inference time.
  - Manual or automatic labelling of `public_test` or `private_test` for tuning is strictly forbidden.
- **Runtime & Scoring Hardware:**
  - Hard limit: $\le 30$ seconds per sample. Timeouts score `0`.
  - Offline inference only (no internet, external APIs, or remote services).
  - Evaluation environment: $1 \times$ NVIDIA A30 GPU, 16-core Intel Xeon Gold 6442Y CPU, 64 GB RAM.
- **Reproducibility:**
  - Must fix all random seeds (Python, NumPy, PyTorch, etc.).
  - Deterministic decoding required (greedy decoding or `temperature = 0`).
  - If re-run results differ from submission, organisers run the Docker image 5 times and use the average score.
- **Tie-Breaking:**
  1. Re-score `tool_calls` using the F1 formula, ignoring the `state_hash` match.
  2. If still tied, the team with lower average processing time per sample ranks higher.
